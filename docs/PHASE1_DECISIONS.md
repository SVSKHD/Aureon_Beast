# Phase 1 Decisions

Ambiguities in ARCHITECTURE.md resolved by the simplest reading. Each is reversible in Phase 1 without touching services.

| # | Spec | Decision |
|---|------|----------|
| 1 | §25 lists states but not every edge | `REQUESTED → CANCELLED/EXPIRED` (wizard abandoned or timed out); `CONFIRMED → CANCELLED` (requester cancels before the executor claims). Nothing may return to `REQUESTED` or `CONFIRMED`. `FAILED_RECONCILIATION` is terminal — manual repair is an operator action outside the state machine, audited separately. |
| 2 | §41 `FAILED_SPREAD_LIMIT` "possible state/error" | Modelled as `status=FAILED` + `failure_code=SPREAD_LIMIT`, not a separate state. Keeps the state graph small; `FailureCode` enum carries the specifics (§56, §78). |
| 3 | §12 hash separator | ASCII unit separator 0x1F, because `event_key` legitimately contains `\|`. |
| 4 | §12 `account_scope` | Config `AUREON_ACCOUNT_SCOPE`, default `"primary"`. Deliberately an alias, not the broker login, so a broker migration doesn't re-key history. **Set this before Phase 2 and never change it.** |
| 5 | §34 comment token | `AUR:` + 6 base32 chars from sha256(request_id) = 10 chars total; deterministic so a crashed executor can re-derive it. |
| 6 | §8 market timezone default | `Europe/Athens` (typical MT5 server clock, DST-aware). Override with `AUREON_MARKET_TZ`. |
| 7 | §18 session times | Placeholder defaults in `config/sessions.py` (Asia 02–10, London 10–18, NY 15–23 market time). Overlap resolved by fixed precedence London → NY → Asia. Bump `SESSION_CONFIG_VERSION` on any change. |
| 8 | §50 inferred links | `TradeRequest` and `Trade` reject `link_type=inferred`; inferred relationships live only in review documents (Phase 7). |
| 9 | §43 pending orders | No separate `pending_orders` collection; `PendingOrder` is a model the monitor uses over the `PENDING` trade request. Add a collection later only if queries need it. |
| 10 | §67 heartbeats | Stored both embedded in `system_state` (for one-read status) and in a `heartbeats/{service}` doc (source of truth the monitor writes). |
| 11 | §56 settings | Firestore `settings/execution` (`ExecutionSettings`) overrides env defaults at runtime; `trading_enabled` defaults to **false**. |
| 12 | §6 schema version | Single integer `schema_version = 1` on every document; per-collection versions can be introduced later without migration. |
| 13 | §22 evaluation status | `INVALID` reserved for horizons that cannot complete (e.g. data gap); a `COMPLETE` horizon must carry all excursion fields (validator). |
| 14 | §23 `reached_N` / `time_to_N` | Stored as `reached: dict[threshold, bool]` and `time_to: dict[threshold, seconds\|None]` rather than 10 named fields, so thresholds are configurable per rule. |
| 15 | Trade `close_reason` | Free string constrained by convention (`sl\|tp\|manual\|mobile\|broker\|discord\|unknown`); made an enum once Phase 5 shows what MT5 actually reports. |

## Decisions added while implementing Phase 2

`docs/ARCHITECTURE.md` is still absent, so §13's exact wording was unavailable and
the EMA-cross rule below is the standard reading. Rows 29 and 31 are the two most
worth checking against the real §13, because they change detection counts.

| # | Spec | Decision |
|---|------|----------|
| 28 | §9 fixture provenance | The committed `XAUUSD_M5.csv` is **synthetic** (seeded random walk via `scripts/gen_fixtures.py`), as no real broker export was available — the spec permits this if stated. It deliberately spans a weekend, so the 49h discontinuity exercises gap handling and Phase 3's `INVALID` horizons rather than leaving them untested. |
| 29 | §13 `sequence_today` / `sequence_session` | Count **candles** within the broker day and session, not detections. The engine must build a context before knowing whether any agent will emit, so a per-agent detection count is not available at that moment; and it is recoverable by querying `detections`, whereas a candle index is deterministic under replay. |
| 30 | §79/§82 engine window | `AnalysisEngine`'s window length is **fixed** and derived from `max(agent.min_window())`, identical in live and replay. This is a **correctness** parameter, not a tuning knob: EMA and Wilder's RSI are recursive, so a 30-bar and a 200-bar window disagree on EMA(21) by enough to move a crossover onto a different candle. `test_a_shorter_window_breaks_parity_as_expected` pins it. |
| 31 | §13 what counts as a cross | A cross is a **change in the sign of `fast − slow`, ignoring bars where they are exactly equal**. Comparing only against the previous bar is wrong either way: treating equality as the opposite side invents a cross for `1, 2, 2, 1` against `slow = 2` (a touch from below that fell back), while requiring strict inequality misses `3, 2, 1` (a real cross passing through equality). Carrying the last non-zero side forward handles both. |
| 32 | §75 backfill warm-up | The observer's backfill reaches back a full `window_size` **before** the cursor, feeds those candles to rebuild the engine's window, and discards their detections. Without this a restart silently produced detections that never existed and missed ones that did — caught by `test_observer_recovery` and pinned there. |
| 33 | §13/§14 RSI's role | RSI is attached as **context only** and never gates a cross. Keeping the gate out means the stored detections record what the crossover rule saw, so "would RSI have helped?" stays answerable from `detection_evaluations` instead of being baked into what was recorded. |
| 34 | §10 weekly schedule | The weekly open/close (Sun 22:00 → Fri 21:00, plus a 60-minute `PREOPEN`) is expressed in **UTC**, deliberately separate from §18's session windows, which are market-local. The weekly boundary is a market-wide convention, not a property of whichever broker clock we read. This is what makes Sunday 21:30 UTC (`PREOPEN`) differ from 23:30 UTC (`OPEN`). |
| 35 | §79 agent window shape | Agents receive a pandas `DataFrame` with a UTC `DatetimeIndex` of candle **open** times and columns `open, high, low, close, tick_volume, real_volume`, oldest first, last row = the candle just closed. `validate_window` rejects anything else so a malformed window fails with a clear message rather than as a wrong indicator. |
| 36 | §83 outbox durability | SQLite in WAL mode with `synchronous=FULL`. The table's entire purpose is surviving an abrupt kill, so trading a real durability guarantee for write throughput on a few detections an hour would be a bad bargain. `delivered_at` is set strictly **after** the remote write returns. |

## Decisions added while implementing Phase 2 Part B

`docs/ARCHITECTURE.md` is still absent, so §14–§18 were unavailable and every agent
rule below is the standard reading. Rows 40, 41 and 44 are the ones most worth
checking against the real sections, because they change what is detected.

| # | Spec | Decision |
|---|------|----------|
| 37 | §79 engine windows | `AnalysisEngine` holds one buffer sized to the hungriest agent but hands **each agent exactly its own `min_window()`**. Without this, window dependence leaks between agents: registering the liquidity agent (583 bars) beside the cross agent (64) would widen the shared window and silently rewrite the cross agent's history, invalidating the recorded baseline just by adding a sibling. `test_an_agent_is_unaffected_by_its_siblings` pins it. |
| 38 | §14 RSI agent | Emits on zone **transitions** (`overbought_entry` / `_exit`, `oversold_entry` / `_exit`), not while a zone holds. RSI sits above 70 for long stretches; emitting throughout would produce hundreds of near-identical detections and bury the bar where the state actually changed. Context-only: `direction` is always `None`. |
| 39 | §18 session trend | Context-only (`direction=None`), although a session that closed higher has an obvious "up" direction. A session summary describes the **past**, and Phase 7's inferred-link rule matches on "same symbol, same direction, trade opened shortly after" (§50) — a directional session detection would attract spurious links to unrelated trades and quietly corrupt the review. The trend is carried as a label plus the numeric change instead. |
| 40 | §15 liquidity sweep | `event_key` is `"{direction}\|{level_type}"` where *direction* is **where price went** (`up` through a high), while `Detection.direction` is the **implied reversal** (an up-sweep is a SELL bias). The two deliberately disagree; conflating them is the easy mistake. This is a strategy claim rather than an observation, so it wants confirming against §15. |
| 41 | §17 breakout | `Detection.direction` **agrees** with the break direction — a continuation, not a reversal — which is the mirror of row 40. A breakout also requires the **previous close on the other side of the level**, so price holding above a level reports one breakout rather than one per bar for the rest of the session. |
| 42 | §15/§17 level timing | Levels are computed as of the **previous** bar. Otherwise a candle can sweep or break a level it helped create, which is trivially true and meaningless. |
| 43 | §15 swing definition | A swing is a fractal pivot: strictly greater (or less) than `strength` bars **on each side**. Strictly, so a flat double top is not a fresh pivot but an already-tested level. A pivot is only reported once `strength` bars have closed after it — reporting an unconfirmed one would use future information, since the bar might yet be exceeded and the "level" vanish. |
| 44 | §15/§17/§16/§18 thresholds | Penetration, rejection, close-beyond, wick ratios and the session flat band are **placeholders**, tuned only to be non-degenerate. They are deliberately permissive rather than restrictive: detections are immutable, cheap and evaluated in Phase 3, so recording a marginal sweep costs little while missing one is unrecoverable. Expect to retune against §15/§17 and against Phase 3's reached-N results. |
| 45 | §18 who writes `sessions/` | The **observer** writes them, not the agent: an agent that touched Firestore would break both the purity contract and the rule that only repositories write (CLAUDE.md). They also bypass the outbox, because a session summary is derived entirely from candles the observer re-processes on restart — a lost write regenerates, so failing loudly would stop observation for something recoverable. |
| 46 | §18 internal day keys | `LevelTracker` groups bars into broker days using **opaque integers** (local-midnight epoch), never formatted date strings — they are only ever compared for equality. Measured over the same workload: per-element `strftime` 1.6s, `DatetimeIndex.strftime` 4.9s, integer keys 0.25s. `tz_localize(None)` is applied first so a DST transition day cannot make the flooring ambiguous. |

## Decisions added while implementing Phase 3

`docs/ARCHITECTURE.md` is still absent, so §21–§23 were unavailable. Row 47 is the
one to read first: it is a finding about the specified thresholds, not a preference.

| # | Spec | Decision |
|---|------|----------|
| 47 | §21 threshold scale | Thresholds are in **points**, consistent with every other distance in the system. At XAUUSD's `point = 0.01` the specified 3/5/10/15/20 are $0.03–$0.20 — far inside a single M5 candle's ~$0.45–1.10 range — so **every threshold is reached on the first candle, in every horizon, 100% of the time**. The rule is implemented exactly as specified and the saturation is reported as a finding rather than quietly retuned: the rule is frozen by design, and the mechanism for a better scale is a new `rule_id`. The report and the baseline both flag it automatically. **Confirm the intended unit against §21 before drawing any conclusion from these numbers.** |
| 48 | §22 evaluation scope | Only detections **with a direction** are evaluated. Without one there is no favourable side, so "did it work?" has no meaning. Context-only detections (`rsi`, `session_trend`, `wick`) are still stored and still available to the reviews as context; the backfill reports how many were skipped for this reason. |
| 49 | §23 same-candle crossings | When the favourable and adverse thresholds are first crossed **within one candle**, their order is unobservable from candle data. §23's wording ("MAE_FIRST if adverse happened *before* favourable; MFE_FIRST otherwise") puts these in MFE_FIRST — the optimistic side. Rather than hide that, a new `path_ambiguous` flag records it so a review can exclude them. On the fixture this is 463 of 470 classifications, which is itself the clearest evidence for row 47. |
| 50 | §22 where evaluation runs | **Inside the observer process**, which the spec offers as one of two options. It needs exactly the closed-candle stream the observer already has; a separate process would mean a second subscription that could drift out of step with the one producing the detections. Finished evaluations are released from memory so a long-running observer does not accumulate them. Splitting it into `main_evaluator.py` later needs no change to the tracker. |
| 51 | §23 excursion timing | A candle's high and low happened *somewhere inside* it, and candle data cannot say when. So the time a threshold was reached is recorded as that candle's **close** — the first moment the crossing is actually known. Using the open would claim knowledge that did not yet exist and make every `time_to` optimistic. |
| 52 | §22 durability | Evaluations are written straight to Firestore, bypassing the outbox. An evaluation is a pure function of its detection and the candles that followed, so a lost write is regenerated by re-running the backfill — unlike a detection, which can never be re-derived once its candle has left the provider's history. |
| 53 | §23 MFE sign | `mfe` is the furthest price ran in the detection's favour and **may be negative**, meaning the best price ever offered was still worse than the reference. That is informative, so it is stored raw rather than clamped to zero. `mae` is its mirror and is normally negative. |
| 54 | §21 `opposite_cross` | Completed by a later detection from the **same agent, symbol and timeframe** with the opposite direction. An opposite-direction detection from a *different* agent is a different opinion, not this agent reversing, so it does not end the horizon. |

## Decisions added while implementing Phase 4 (the money phase)

`docs/ARCHITECTURE.md` was still absent, so **§41, §56 and §57 — the guard's bullet
list — could not be read**. Row 55 is the most important row in this document: it states
what the guard checks and why each rule is there, entirely as inference. A guard missing
a bullet is a money-losing bug, and only the frozen spec can say whether one is missing.

| # | Spec | Decision |
|---|------|----------|
| 55 | §41/§56/§57 guard rules | Seventeen rules, each its own function with its own test: `trading_enabled`, `symbol_allowed`, `confirmation_fresh`, `market_open`, `symbol_available`, `quote_available`, `quote_fresh`, `spread_within_limit`, `price_has_not_run_away`, `volume_valid`, `volume_within_max_lot`, `filling_mode_supported`, `stops_valid`, `pending_entry_valid`, `margin_sufficient`, `within_open_position_limit`, `within_daily_trade_limit`. Every "cannot tell" answer is a **refusal**, not a pass. **Reconcile this list against the real §56/§57/§41 before trading a funded account.** |
| 56 | §41 deviation | The guard **clamps** the requested deviation to `max_deviation_points` and never widens it. A request asking for more slippage tolerance than policy allows gets policy's. |
| 57 | §41 price drift | `price_has_not_run_away` compares the execution-time price against the **confirmed** quote and refuses only **adverse** movement beyond `max_deviation_points`. Refusing a fill that improved on what the human saw would be perverse. Distinct from the spread rule, which measures the book's width rather than its movement. |
| 58 | §30 unmapped broker retcodes | An unrecognised MT5 retcode is treated as a **rejection**, not an unknown outcome: the broker returned a code, so it did decide. Only the *absence* of an answer (a raised exception, a `None` result) leaves the request `EXECUTING`. Getting this backwards would either strand good requests or invite a re-send. |
| 59 | §35 reconciliation matching | Matched on magic + comment token + symbol + direction, with volume as an **upper bound within tolerance** rather than an equality — a partial fill is a legitimate match with a smaller volume, and insisting on equality would make every partial fill unfindable. Deals sharing a `position_id` are collapsed into one candidate, so a multi-deal fill does not look like multiple orders. |
| 60 | §35 ambiguity | More than one matching broker record → `FAILED_RECONCILIATION` with the candidates listed, never a guess. Two matching orders means something already went wrong, and picking one could attach the request to the wrong position. |
| 61 | §35 a vanished pending order | A `PENDING` order that is no longer at the broker and never filled resolves to **`CANCELLED`**, not `EXPIRED`. Claiming expiry would assert an expiry time we never observed. |
| 62 | §29 the stale-claim rollback | `claim` writes `FAILED_STALE` and **returns**; the refusal is raised by the caller *after* the commit. Raising inside the transaction aborts it and rolls the write back, leaving the request `CONFIRMED` and claimable later at a price the human never saw. This was a real bug, caught by scenario D. |
| 63 | §32 same-status resolves | `resolve` short-circuits only when there is genuinely **nothing to write**. An earlier version returned early on any unchanged status, silently discarding the `comment_token` the executor stamps before sending — leaving reconciliation nothing to search for. Also a real bug, caught by scenario A. |
| 64 | §87 test substrate | The failure-injection suite runs against the **real Firestore emulator**, via `make emulator` (Node + Java, no Docker) or `docker-compose.emulator.yml`. Exactly-once rests entirely on Firestore's transaction semantics, so an in-memory double would be testing my model of those semantics rather than the semantics. Without `FIRESTORE_EMULATOR_HOST` the suite **skips loudly** rather than passing vacuously. |
| 65 | §87 emulator behind a proxy | gRPC honours its own proxy variables, so a session with `HTTP(S)_PROXY` set cannot reach a localhost emulator (`Expected SETTINGS frame as the first frame`). `no_grpc_proxy=127.0.0.1,localhost` is the targeted bypass; the Makefile sets it. This disables nothing else. |
| 66 | §56 settings failure | `ExecutionSettingsRepository.read_or_default` returns `ExecutionSettings()` — i.e. `trading_enabled=False` — when the document is missing or unreadable. An absent settings document must not become an open trading bot. |

## Decisions added while implementing Phase 5

`docs/ARCHITECTURE.md` was still absent, so §36, §44, §45 and §52 are inferred.

| # | Spec | Decision |
|---|------|----------|
| 67 | §49 trade document id | `{account_scope}__{mt5_position_id}`, deterministic. The monitor re-sees every position on every poll and after every restart; a random id would accumulate one document per sighting. `account_scope` is included because two accounts can legitimately hold the same position id. |
| 68 | §44 realized P&L | The **sum of the deals' profit**, plus commission and swap, exactly as the broker reports them — never recomputed from prices and volumes. A recomputation would silently disagree with the account statement the moment a contract size, a currency conversion, or a two-price partial close is involved. The broker's number is the one the money followed. |
| 69 | §36 exit matching | Exits are matched on `mt5_position_id` + deal `entry` type, **never on the comment**. A closing deal often carries no comment, or one the broker wrote itself (`"sl 2398.00"`); matching exits by comment would miss every stop-loss and every close from a phone. The comment is still used for *entries* (Phase 4), where it is the only way to find an order whose result was lost. |
| 70 | §44 close price and reason | Taken from the **last** exit deal by time — the price the position finally left the market at. Deals are sorted before folding, because broker history can arrive out of order. |
| 71 | §44 incomplete exit evidence | A position gone from the broker's open list whose visible deals do **not** account for its full volume is recorded `PARTIALLY_CLOSED`, not `CLOSED`. `CLOSED` is terminal, so closing on partial evidence freezes a wrong `realized_pnl` that no later poll can correct. Caught by a test; a broker timestamp one second ahead of ours is enough to trigger it. |
| 72 | §44 deal window | The deal query reaches back `DEAL_OVERLAP_SECONDS` before the last sync **and 60s forward** of now. Backward because a deal can be published slightly out of order; forward because the broker's clock is not ours and a deal stamped ahead of us would otherwise be invisible for a whole poll — long enough to see only part of a multi-deal exit. Re-reading is free: every write here is idempotent. |
| 73 | §45 excursion units and side | Points, signed by the position's direction, so a BUY and a SELL are directly comparable — the same convention the detection evaluator uses. Measured at the **exit** side of the book (bid for a long, ask for a short), because that is the price the position could actually be closed at; the mid would flatter every excursion by half the spread. |
| 74 | §45 the weaker label wins | A position resuming live tracking over **reconstructed** figures keeps the `reconstructed` label. The record must describe the weakest measurement it contains, not the most recent one. Reconstruction also ignores candles outside the position's life, or someone else's price action gets attributed to this trade. |
| 75 | §45 first observation | The first observed price sets **both** extremes, so `mae` can legitimately be positive early on ("the worst it got was still in our favour") for the same reason `mfe` can be negative. Both are stored raw rather than clamped. |
| 76 | §52 what counts as external | No Aureon magic, **or** Aureon magic with no matching request → `source=external_mt5`, `trade_request_id=None`. The second case matters: our magic without a request means we cannot account for it, so it is observed and never managed. |
| 77 | §43 pending order resolution order | A **fill is checked first, always** — before expiry, before cancellation. An order can fill in the same instant a cancel is issued (Phase 4 scenario G), and recording `CANCELLED` for a position that actually exists would leave a live trade nobody is watching. That is the worst of the three mistakes by a wide margin. |
| 78 | §58 monitor independence | The monitor polls regardless of `trading_enabled`. That switch stops the executor; positions opened before it was thrown are still live and still need their closes recorded. A monitor that paused alongside the executor would blind the operator during exactly the incident that made them disable trading. A test asserts the monitor makes no order-placing broker call at all. |

## Decisions added while implementing Phase 6

`docs/ARCHITECTURE.md` was still absent, so §37–§47, §57 and §71 are inferred. Rows 79
and 80 resolve a genuine contradiction in the constraints rather than an ambiguity.

| # | Spec | Decision |
|---|------|----------|
| 79 | §39/§42 vs CLAUDE.md | §39 requires Discord to build the execution-mode selector from `symbol_info.filling_modes`, and §42 requires it to validate a lot against the broker's min/max/step — but **Discord may never call the broker**. Resolved by having the observer publish `SymbolInfo` to `symbol_specs/{symbol}`, which Discord reads like everything else. The copy is a **convenience, not an authority**: it can be stale, so Discord's validation is advisory and the execution guard re-reads the live symbol (§56). A *missing* copy therefore does not block a trade. |
| 80 | §40/§27 vs "tick data never goes to Firestore" | §40 requires bid/ask on the confirmation screen and §27 requires a quote-age check, but Discord cannot call the broker and tick data may not go to Firestore. Resolved with `SymbolState.last_quote`: **one current snapshot per symbol, overwritten in place** and throttled with the rest of `system_state`. That is state, not a tick stream — the prohibition is about volume and append-only history, and this is neither. When no quote has been published, `check_confirm_press` treats it as "cannot confirm, refresh" rather than as permission to proceed. |
| 81 | §37-§57 layering | All Discord logic lives in `aureon/discord/service.py`, which **imports no discord.py**. The rules that protect real money — who may confirm, whether a quote is too old, whether a lot is legal — are therefore tested directly, without a gateway, a guild or an event loop. `bot.py`, `commands/` and `views/` are thin adapters that render the results. |
| 82 | §71 async discipline | Firestore's Python client is synchronous, so every call from a handler goes through `BotContext.run` → `asyncio.to_thread`. Not an optimisation: discord.py must acknowledge an interaction within three seconds, and a synchronous round trip on the event loop can miss that and lose the interaction entirely. Every handler `defer()`s first for the same reason. |
| 83 | §27 stale quote behaviour | A stale quote **re-prompts**, it does not refuse. The human still wants the trade; they need current numbers. A refusal would make them restart the wizard for a reason that is not about their intent. |
| 84 | §57 switch asymmetry | Disabling trading is **immediate, with no confirmation step**; enabling requires a confirming press. Disabling is the safe direction and the one reached for during an incident, so it must not have a speed bump. Enabling arms real money and deserves the pause. |
| 85 | §46/§47 control requests | Discord writes a `control_requests` document and stops — it does not call the broker, and it does **not** report the outcome from its own return. The executor performs it under the same claim/lease discipline as a trade, and the monitor records what happened. A cancel can lose a race to a fill and a close to a stop-loss; reporting "cancelled" optimistically is how a human comes to believe an order is gone when it is a live position. |
| 86 | §71 startup validation | `main_discord.py` refuses to start without a token **or** without a non-empty allowlist. An empty allowlist authorises nobody, so the bot would answer no one while appearing healthy — worse than a clear failure. A missing guild id is only a warning, but a loud one: a global command would appear in every server the app joins, and this one places trades. |
| 87 | §8 result reporting | A request's outcome is reported by a Firestore listener on that document, never from the CONFIRM button's return. **Every terminal status renders, including the failures**, with the reason the executor recorded. A human who authorised real money and heard nothing back has been failed worse than one who was told it was rejected. |

| # | Spec | Decision |
|---|------|----------|
| 88 | §61-§63 scheduling | Reviews run as a **separate `main_review.py` process**, not a job inside the observer. A review is batch aggregation over history: it needs no live feed, and coupling a minutes-long read of thousands of documents to the loop that must not miss a candle close would trade a real-time guarantee for a reporting one. It must also be re-runnable for any past period — to backfill, or to regenerate after a bug fix — which a CLI makes one command. Reviews are idempotent, so running one twice is harmless. Scheduling is left to cron or a systemd timer; the command defaults to the most recently *completed* period, so "run it after close" is the whole configuration. |
| 89 | §63 period boundaries | A review covers a **broker** day or ISO week, as a half-open `[start, end)` window in UTC derived from market-local midnight. Half-open so consecutive periods tile without double-counting the boundary instant, and market-local because 23:30 UTC is already tomorrow in Athens — a UTC-bounded review would file a session under the wrong day and every per-day figure would be subtly wrong with nothing in the output revealing it. ISO weeks rather than a broker convention, because ISO is unambiguous across year boundaries. An emulator test pins the exact boundary: 21:00 UTC belongs to the next broker day, 20:59 to the previous one. |
| 90 | §61 reached counts | The reviews package may read **only** `complete_horizons`, `pending_horizons` and `invalid_horizons` — never `.horizons` directly. An AST-precise boundary test enforces it. Folding an unknown outcome into a denominator is the single easiest way to make a strategy look worse than it is, and the resulting figure ("3 of 10 reached") is indistinguishable from an honest one. `pending_horizons_excluded` and `invalid_horizons_excluded` are reported on every review so a reader can tell "3 of 10" from "3 of 10, 40 still unknown". |
| 91 | §50 inferred links | An inferred detection→trade link lives **only on the review**, never on the trade, and `InferredLink` requires a `confidence`. Reviews therefore write only their own documents: analysis must not edit the record it analyses. A link is inferred only when **all four** hold — same symbol, same direction, trade opened strictly after and within `AUREON_INFER_WINDOW_MINUTES`, same session — and at most one detection is linked per trade. `confidence` is a rank for ordering candidates, not a probability; nothing may treat it as one. An explicit link is left exactly as the human stated it. |
| 92 | §64 classification | Execution vs observation uses six values, and `UNKNOWN` is one of them: a detection whose horizon is still PENDING or INVALID classifies as `UNKNOWN`, never as `MISSED_AND_NOT_REACHED`. A trade with no link at all is `DISCRETIONARY` rather than an error — humans trade for reasons the machine never saw. The counts are rendered in `notes` with every value named including the zeros, because a reader who cannot see how much was unresolved cannot judge the rest. |
| 93 | §61 review determinism | Regenerating a period **overwrites the same document id** and must produce byte-identical content: a period has one answer, and if the answer changes the old one was wrong rather than also true. Every collection is sorted before folding and no wall-clock value enters the result except `generated_at`, which the caller supplies. Tests assert byte-identity across re-runs and stability under input reordering. |
| 94 | §61 capability split | `/status` holds `ReviewReader`, which has **no write method**, not `ReviewRepository`. A human interface able to rewrite a review would make every figure built on those reviews unfalsifiable. The split is visible in the import graph and enforced by a boundary test, rather than resting on nobody calling the wrong method. This was written because the boundary test caught the repository being wired into the Discord context. |
| 95 | Phase 7 gate | `docs/PHASE2_BASELINE.md` carries a **Weekly review reconciliation** section, and `scripts/gen_baseline.py` refuses to write the document when it does not reconcile — a stale baseline is recoverable, one asserting counts that disagree is worse than none. The two paths are genuinely independent: the baseline counts with a `Counter` over the engine's output, the review with market-clock week windows and COMPLETE-only reached counts. Verified load-bearing by reverting: bounding the week in UTC moves one detection and is caught; folding PENDING into the denominator is caught on four horizons. |
| 96 | §63 weekly default | The weekly review's default period is the **most recently finished trading week**, not "seven days ago": take the most recently completed broker day, walk back to the most recent Friday at or before it, and take that Friday's ISO week. §63 asks for the review to be generated after Friday's close, and subtracting seven days names the week *before* the one that just traded on Friday, Saturday and Sunday — so the cron the spec describes would produce last week's numbers under this week's heading, with nothing in the document revealing the substitution. Found by a test of the CLI's defaults; every weekday is now pinned, plus a year-long invariant that the default never names a week still trading. |

| 97 | §12 detection id | `detection_id` = sha256 over `account_scope`, `symbol`, `timeframe`, `candle_close_utc`, `agent_name`, `agent_version`, `event_key`, joined by `0x1F`, in that order. This **reverses decision 16**, which excluded `agent_version`. The consequence is deliberate and must be understood before bumping any agent: a version bump now *forks* history rather than upserting it — the new version's detections sit beside the old version's for the same candles. That is what lets `ema_cross` 1.0.0 (9/21) and 2.0.0 (20/50) describe the same week side by side, and it is also why a version bump must never be used to correct history in place. The timestamp also moved from the candle **open** to the candle **close**, the instant the detection became knowable. `DETECTION_ID_COMPONENTS` names the tuple so a test pins the contract rather than a hash, and `docs/CONTRACTS.md` now generates the component table. |
| 98 | §12 migration | `scripts/rekey_detections.py` copies mis-keyed detections to their §12 id; it does **not** move them unless `--delete-old` is passed, and it refuses to write outside the emulator without an explicit acknowledgement. It is idempotent: a second run reports the copies as `unchanged` and issues no writes. **It cannot split a collision the old recipe already caused** — because the old id omitted `agent_version`, two versions of one agent observing the same candle wrote to the same document and the second overwrote the first. Only one survived. The 9/21 history therefore comes from replaying with that agent, not from this script. |
| 99 | §13 EMA periods | `AUREON_EMA_FAST` (20) and `AUREON_EMA_SLOW` (50). `EmaCrossAgent` takes **no default periods at all** — both are required keyword arguments. A default is the specific bug the signature prevents: the observer would read 20/50 from config while a replay, script or test silently constructed 9/21, and the two would disagree about which candles produced a cross while both looked correct. Added to `aureon/config/config.py` rather than a new `aureon/config/settings.py`, so configuration stays in one module (`aureon/models/settings.py` already exists and holds the Firestore runtime gates — a third settings location would be worse than the naming mismatch). |
| 100 | §13 cross numbering | On a cross detection, `sequence_today` / `sequence_session` are the **cross ordinal** (1st, 2nd, 3rd of the day and of the session), not the candle index. Every other agent keeps the candle index, where the index *is* the meaningful ordinal. Numbering happens in the **engine**, not the agent: an agent is a pure function of `(window, ctx)`, counting across candles is state, and state in an agent would break the replay/live parity contract. §12 excludes the sequence, so re-numbering cannot re-key a detection. |
| 101 | §66 cross counters | Six counters on `SymbolState`, reset on the **market** clock: `ema_crosses_today/session`, `bullish_crosses_today/session`, `bearish_crosses_today/session`. Six rather than two because "4 crosses today" and "3 up, 1 down" answer different questions and neither is derivable from the other. A day reset clears the session tallies too (a day contains its sessions); a session change leaves the day tallies alone. The observer reads them from the engine rather than recounting, so a second tally cannot drift from the first. |
| 102 | §21 threshold units | `EvaluationRule.threshold_unit` is `points` or `price`. `EMA_OUTCOME_V1` stays `points` and is **frozen** — a test pins its `definition_hash`, so editing its thresholds fails with the rule named rather than silently redefining every result already stored under `{detection_id}__EMA_OUTCOME_V1`. `XAU_OUTCOME_V2` uses the same horizons and reference price with thresholds `[3, 5, 10, 15, 20]` in **price**. The points equivalent is **derived from `symbol_info.point` at evaluation time** (`thresholds_in_points`), never a hard-coded multiplier, so the rule means "$5" on any symbol. V1's 3–20 points at `point=0.01` is $0.03–$0.20, inside a single XAUUSD M5 candle — which is why every V1 threshold read as ~100% reached and measured the tick size rather than the strategy. |
| 103 | §21 default rule | `AUREON_EVAL_RULE` defaults to `XAU_OUTCOME_V2`. The older `AUREON_EVALUATION_RULE_ID` still wins when set, so an existing `.env` pinning V1 keeps getting V1 rather than silently switching to a rule with different thresholds — for a variable that decides which numbers you get, the safe direction is to honour the explicit pin. |
| 104 | §75 restart reach-back (**bug fixed**) | The observer's backfill reaches back a window's worth of **candles**, not of minutes. `_reach_back` widens its request until it actually yields `window_size` candles at or before the cursor. The old code computed `cursor - window_size × timeframe`, which is only equivalent while the market never closes: restarting in the ~151 candles after the fixture's 49-hour weekend gap, the request landed *inside* the gap and returned 72 of the 151 needed, so the fresh engine's EMAs never converged and the restart **silently lost a detection the uninterrupted run produced**. This was a latent bug all along — the 9/21 pair survived it by coincidence, needing only 64 bars of reach, which happened to fit in the six hours of candles after the gap. It surfaced the moment the warm-up grew to 150. Kill points 1429 and 1500 in `test_restart_produces_no_duplicates_and_no_gap` pin it; reverting the fix fails both. The widening deliberately does **not** stop when a doubling returns no new candles, because "asked for earlier candles and got none" is indistinguishable from the start of history — an early exit on the first unchanged count is exactly what left the reach-back starved. |
| 105 | §19, §23 context tags | Four tags on each evaluation — `has_lower_rejection_wick`, `has_upper_rejection_wick`, `sweep_same_direction_within_N_candles`, `session_trend_aligned` — derived **only** from detections at or before the subject's own candle close, within `AUREON_CONTEXT_WINDOW_CANDLES` (default 3). This module is the easiest place in the system to leak the future: "look at the detections around this one" has no natural sense of direction in time, and a wick forming on the *next* candle would tag the cross retroactively, manufacturing a correlation that looks real and cannot be falsified. One line in `window_for` enforces it and four tests catch a symmetric window. A `flat` session trend is never alignment — calling it aligned would put every flat session in the "aligned" bucket for both directions. Tags live on the evaluation, never on the detection, because a detection is immutable and must carry no information about its surroundings that was not in its own candle. |
| 106 | §23 tag comparison | The review reports each tag as **both** sides — `with` and `without` — from COMPLETE horizons only. A "with" rate alone is unreadable: 60% means nothing until the "without" number is known. A comparison whose either side has fewer than 5 COMPLETE horizons is labelled "too few to read" rather than printed as a percentage, because at those counts one detection moves the rate by twenty points. The comparison is printed by `main_review.py`, not stored on the review document: it is explicitly research, and a week of 29 crosses cannot support a claim either way. An evaluation with no tags at all counts as `without` rather than being dropped, so an older document cannot silently shrink the denominator. |
| 107 | §57, §60 kill switch | `set_trading_enabled` writes the settings document **and** its `AuditRecord` in ONE Firestore transaction, with a `settings_version` read-then-conditional-write. Previously it was read-modify-write plus a separate audit write: two concurrent toggles were last-write-wins on the one setting that decides whether real money can move, and the switch could flip with no audit row (or leave a row for a write that failed, which is worse — it claims something happened that did not). `if_version` lets a caller assert what it believed it was changing, for a UI that read the settings, rendered a button and got a press seconds later. The audit id is **deterministic** per version, so a transaction Firestore retries writes the same row rather than claiming two decisions where a human made one. |
| 108 | §58 terminal immutability | A terminal request (`FILLED`/`CANCELLED`/`EXPIRED`/`FAILED*`) or trade (`CLOSED`) refuses any field write except `last_reconciled_at` / `last_synced_at`. Both are observational: they record when something was last looked at and assert nothing about what happened. The guard covers the gap the transition table cannot see — a **same-status** write carrying `updates`, which could rewrite a settled trade's `realized_pnl` and make every review built on it unfalsifiable. Ordering matters: the transition table is consulted first for an actual status change, so `CLOSED → OPEN` still reports itself as an illegal edge rather than as a terminal write. The `EXECUTING → EXECUTING` path that stamps `comment_token` is explicitly preserved and tested — breaking it would trade one silent failure for a much worse one. Terminal sets are derived from the transition tables, so adding a terminal state protects it automatically. |
| 109 | CLAUDE.md repository boundary | Every raw Firestore read moved into a repository method, and two AST boundary guards replace the old import-only check: nothing outside `aureon/storage` may call `.collection(`, `.document(` or `.transaction(`, and nothing may reach into another object's `_client`. Six call sites existed — four in the review service, one in the Discord listener, one in the executor reaching into `repository._client` behind a `noqa`. All six were reads, which is exactly why this mattered: the rule meant to prevent a client-side money write did not constrain that shape of code at all, so the next raw call could have been a `.set()` and the suite would have stayed green. Resolving it exposed a genuine conflict between two CLAUDE.md rules — routing reads through repositories forces reviews to import write-capable classes, which §50 forbids — settled by `PeriodReader`, a read-only composition living inside `aureon/storage` with no write method, the same pattern and the same reasoning as `ReviewReader`. |
| 110 | §46, §47 control leases | `control_requests.resolve` verifies lease ownership exactly as trade requests do, with `reconciliation=True` as the same sanctioned exception. This was an asymmetry, not a decision: without it an executor whose lease had expired could still record the outcome of a cancel it no longer owned, and since a cancel can lose a race to a fill, a stale `completed` landing on top of the real `already filled` is how a human comes to believe an order is gone when it is a live position. `ControlWorker` also stopped passing the *claim* time to `resolve`, which would have let an operation that outran its lease pass the check it exists for. The missing two-executor scenario test is now present: one cancel, two workers, exactly one broker cancel. |
| 111 | §83 collection prefix | Every collection is `{AUREON_COLLECTION_PREFIX}_{name}`, default `aureon_beast`. `paths.collection()` is the only place a name is built, the constants keep their names and hold prefixed values (so every existing caller is already correct), and a boundary test forbids a bare collection literal anywhere under `aureon/` outside `paths.py`. A bare literal is the worst kind of bug here because it does not fail: reading `"detections"` while everything else uses `"aureon_beast_detections"` silently touches a second, empty collection, which looks exactly like "no data yet". The prefix is read from the environment **at import time** in one module rather than threaded through the repositories — a prefix that differed between two repositories in one process would split the database in half with both halves reporting success. An empty or all-underscore value falls back to the default rather than producing `_detections`. `tests/conftest.py` sets `aureon_test` **before any aureon import** (later would be too late, since `paths` freezes the value) and refuses to run on the production default without an emulator host. The emulator rules already match `{document=**}`, so they need no change; the real client-facing rules are still Phase 8. |
| 112 | §59, §66 market snapshot | `SymbolState` carries the full live picture: `ema_fast/slow/distance`, `rsi`, `rsi_zone`, `session`, `session_trend`, `session_high/low`, the six cross counters, `last_cross {direction, at, price, detection_id}`, `last_cross_at`, `last_sweep`, `last_wick`, `last_breakout`, `detections_today`. Written on every candle close; the quote and heartbeat fields stay on the existing throttle. `MarketSnapshot` assembles it **from the detections the engine already produced**, reading each detection's own `IndicatorSnapshot` rather than recomputing anything — a second implementation would, the first time the two disagreed, make the status screen quietly wrong about a number a human was using to decide something. The consequence is deliberate: a field stays `None` until an agent has emitted a detection carrying it, so a fresh start reports "unknown" rather than guessing. Session extremes come from candles, not detections, because a session has a high whether or not anything detected anything. A new broker day clears `detections_today` and the session extremes but **keeps the EMAs** — an EMA does not reset at midnight, and blanking it would make the screen claim no information on the first candle of every day. `observe` is idempotent per detection id, because the restart backfill replays candles it already processed. |
| 113 | §59 two status modes | `/status` is live **or** review, never both. On an OPEN market it renders the §59 panels; on a CLOSED market those numbers are a snapshot of whenever the market shut, and rendering them in a live layout invites reading them as current — so the closed screen shows the completed review instead, which is what a reader wants after the close. A missing value renders as an em dash, never `0.00`: a zero is a measurement and a dash is the absence of one, and on a line reporting "how far apart are the EMAs" a zero claims they have converged. The panel keeps its shape when values are missing, so it does not change layout as data arrives. `ema_distance` and `rsi_zone` are stored so a dashboard need not re-implement "where does overbought begin", but they are **derived in a model validator** whenever absent, so a document carrying an EMA pair always carries the matching distance and the two cannot drift apart. |
| 114 | §82 live-candle archive | The observer writes every closed candle it processed to `data/live_candles/{symbol}_{tf}_{market_date}.parquet`. The replay/live parity test proves the engine is deterministic **given the same candles**; it cannot prove the live path was given the same candles, because the live input only ever existed in memory. Without the archive, a live session producing different detections from a replay leaves no way to tell whether the engine drifted or the broker served different bars — and those two have completely different fixes. Parquet rather than CSV because a CSV round trip turns a float into a string and back, which is precisely where a comparison acquires a difference that was never in the data. Filed by **broker** date: a 22:00 UTC candle belongs to the next trading day in Athens, and a UTC-named file would split one session across two so a comparison for "Monday" would silently miss its first three hours. Buffered and flushed on day rollover and shutdown, merging with whatever is on disk — a restart mid-day that truncated the morning would make every missing morning detection read as a live/replay mismatch. A closed candle is not tick data: it is the same bounded, final record the detections are derived from. |
| 115 | §82 comparison | `scripts/compare_live_vs_replay.py` replays the **archive**, never a fresh broker fetch — a refetch would let "the broker served different candles the second time" masquerade as an engine difference. It reports three distinct kinds because they have different causes: *missing* (replay produced it, live never stored it — look at the outbox, then the window), *extra* (stored but not reproduced — usually a leftover from an earlier `agent_version`, which is exactly what §12 is for), and *mismatched* (same id, different content — the most serious, since the id is a pure function of the candle). `schema_version` is excluded from the content diff: it is metadata about the document, not about the observation, and including it would make a schema bump report thousands of mismatches and bury a real difference. Exits non-zero on any difference so it can gate a session review. The manual leg is `docs/MT5_SESSION_CHECKLIST.md`; `docs/PHASES.md` carries an explicitly **empty** "Phase 2 real-session evidence" section, because a section that did not exist would read as an oversight where an empty one reads as a gap. |

It was extended after the prefix landed and immediately found a real one: `stored_ids` in `test_observer_recovery.py` filtered on `"detections/"`, which matched nothing once collections were prefixed. The negative assertions then passed **vacuously** — empty list versus empty list — and only a single positive assertion failed. That is why a stale literal in a test helper is worse than one in production code: most of the test keeps passing and says nothing. |

It has to: the test suite runs under `aureon_test`, so a generator that emitted the resolved prefix produced a document that could never satisfy `--check` in both a test run and production. The document describes the shape of the database; which prefix a given deployment uses is a deployment fact, and the file says so in a line above the table. |
| 118 | §22 evaluation coverage (D-4) | The outcome tracker filters on **direction, not agent name**, and always has — it has no allowlist.
